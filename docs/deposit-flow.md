# Fidere Deposit Flow

本文件记录 2026-08-27 对 Sandbox 的勘察、自动化设计和受控E2E状态。所有真实写操作仍受双安全开关、单次点击和零重试约束。

## 业务边界

客户端存在两条不同的“入金”路径，必须分开建模：

| 路径 | Client入口 | 业务性质 | 当前自动化边界 |
| --- | --- | --- | --- |
| 银行电汇入金 | `账户` -> `存入资金` / `银行存入` | Client填写入金申请，Admin在`入账认领`处理 | DP-001、DP-002、DP-003和只读Reconciliation均已完成 |
| 数字资产注入 | 首页`接收`/资产行`转入` | 展示钱包、资产和网络，由链上/托管入账 | 只读；依赖外部钱包或链上Sandbox |

## Client银行电汇入金

- URL：`/zh-CN/account/fund-in?fromAccountType=trust`
- Page Object：`pages/client/DepositPage.ts`、`pages/client/TransactionsPage.ts`、`pages/client/TransactionDetailDrawer.ts`
- 支持账户与币种：

| 账户 | 币种 |
| --- | --- |
| 香港账户 | 港元、美元 |
| 美国账户 | 美元 |
| 新加坡账户 | 港元、美元、新加坡元、阿联酋迪拉姆、日元 |
| 巴林账户 | 港元、新加坡元、人民币、美元、欧元 |

表单实际字段：收款账户、币种、打款银行、入金金额、打款渠道、打款用途、资金来源、可选转账附言。Client不要求填写收款银行资料，也没有上传凭证字段；页面直接展示平台收款银行信息。最终按钮为`提交`。

页面接受两位小数金额。页面没有展示最低/最高金额；金额为空时提交禁用，金额0的最终服务端规则仍未通过提交确认。历史记录存在`11.00`金额，因此首次受控写执行建议使用可复现的`11.xx HKD`，但运行前仍必须以页面校验结果为准，不得自动提高金额重试。

Client全局`交易流水`显示法币转入类型、账户、金额、状态、时间和系统`TXN-*`。点击唯一记录可打开`法币转入 详情`，读取状态、金额、手续费、创建日期和账户。2026-08-27的现有DP-003记录中，详情同名“交易编号”字段显示Client电汇指令参考号`AUTO_DP003-*`，并非列表系统TXN；自动化分别保存两者，不替换或推导语义，也不保存完整响应、账户或身份信息。

## Admin入账认领

- 入口：`运营` -> `法币资产管理` -> `入账认领`
- URL：`/zh-CN/operation/fiatAssets`，tab不改变URL
- Page Object：`DepositClaimListPage`、`DepositClaimDrawer`、`DepositRejectDrawer`
- 列表筛选：状态、匹配状态、开始/结束日期、参考号/付款人/备注关键词
- 状态：待处理、处理中、处理完成、处理失败
- 列表字段：提交时间、账户类型、币种/金额、实际入账金额、付款人、渠道、参考号、转账凭证、匹配客户、匹配状态、状态、操作

Admin列表和操作抽屉没有独立订单编号，也不显示Client `TXN-*`。参考号可以为空，因此Client/Admin不能稳定按编号直接关联。

受控DP-002提交进一步确认：Client填写的`转账附言`不会回写为Admin列表的`参考号`，Admin仍显示`-`。因此附言/参考号不得作为强制匹配条件；唯一候选依赖客户稳定指纹、账户、币种、精确金额、状态、渠道和可靠提交时间。

认领抽屉显示原始来账金额、可认领入账金额、账户类型、付款人、渠道、参考号、提交时间、匹配客户；`认领备注 *`必填，最终按钮是`确认认领`。可认领金额是可编辑输入项，所以DP-003必须把实际认领金额纳入Primary Oracle。

拒绝抽屉要求`拒绝原因 *`，最终按钮是`确认拒绝`。本轮只打开并关闭两个抽屉，两个最终按钮点击次数均为0。

## 唯一候选策略

Admin阶段按以下业务指纹定位，不取第一条或最新一条：

```text
匹配客户稳定标识/不可逆哈希
+ 账户类型
+ 币种
+ 精确申请金额
+ 待处理状态
+ 打款渠道
+ Client提交时间窗口
```

只有`candidateCount === 1`才允许未来进入Admin写操作。当前历史Reconciliation从43条待处理记录依次筛选为：账户20条、币种3条、金额1条、状态1条、渠道1条、时间1条、用户1条。Admin客户单元格只显示名称，因此自动化使用标准化文本的SHA-256指纹匹配，配置和报告不保存客户姓名或邮箱。

## 首条E2E建议

| 项目 | 建议 |
| --- | --- |
| 账户/币种 | 香港账户 / USD；复用Transfer已验证的公共账户余额读取能力 |
| 金额 | 可复现的`11.xx USD`；两位小数已通过Validation |
| Client编号 | `TXN-*`；提交后从交易流水唯一行读取，并打开对应详情完成业务字段交叉验证 |
| Admin编号 | 当前页面无独立编号 |
| Admin处理 | 唯一候选详情二次核对后，填写备注并单次认领或拒绝 |
| 余额Oracle | 香港账户USD可用余额可直接读取 |
| 数据恢复 | 当前无冲正/重置能力；真实认领会永久增加余额和审计记录 |

Sandbox银行电汇入金不依赖外部银行/BaaS回调：Client提交后会直接进入Admin`法币资产管理 -> 入账认领`。因此DP-002/DP-003属于可控的Client + Admin E2E；当前剩余限制是无冲正/余额重置能力，不再把外部回调列为阻塞项。

## Oracle分级

DP-003 Primary Oracle：

1. Client交易流水存在唯一入金记录，且该记录具有真实`TXN-*`系统编号并可打开详情。
2. Admin业务指纹候选唯一。
3. Admin认领详情与Client申请一致。
4. Admin处理成功并进入成功终态。
5. Client原申请进入成功终态。
6. 目标法域账户余额增加`actualDepositAmount`。

DP-002 Primary Oracle：Client原申请创建、Admin候选唯一、拒绝详情匹配、Admin拒绝终态、Client原申请拒绝/失败终态、目标余额没有不应有的增加。

Secondary Oracle：Client全局交易流水、全局TXN展示、邮件通知、非核心详情字段。Secondary失败只产生Warning，不覆盖已经成立的核心资金结果。

DP-002/DP-003真实执行必须同时临时开启`ALLOW_MONEY_TESTS=true`和`ALLOW_ADMIN_MUTATION_TESTS=true`，使用`workers=1`、`retries=0`、禁止`repeatEach`，Client提交和Admin最终操作都最多一次。任何结果不明确时只能Resume原TXN，禁止创建第二笔入金。

DP-002的首次编排在Client成功页文案断言和后续总测试时限处中断，历史失败报告保留；流程随后只Resume原申请并以只读Postcheck完成业务判定，没有创建第二笔入金、没有第二次Admin拒绝。修复后成功页使用`入金申请已提交`标题，Client记录加载使用`expect.poll`，跨系统Mutation用例使用独立的合理总时限。
