# Fidere Client + Admin Automation Blockers

本文件记录 Client、Admin 和 Client + Admin 闭环进入下一阶段前需要解决或明确的阻塞项。

客户端 storageState 轮换问题已通过 `client-auth` Setup Project 解决：每次 Client 命令自动登录一次并覆盖 `auth/client.json`。Admin 图形验证码与人工状态采集逻辑保持不变。

## 需要 Admin 的流程

| 流程 | 原因 |
| --- | --- |
| 资金互转 / 券商资金划转 | `提交审核` 后由 FIDERE Trust 审核及处理 |
| 开户 / 券商开户 | 开户申请需要后台审核、资料审批和券商状态同步 |
| 出金 / 发送资产 | 资产转出通常需要风控或运营审核，至少需要后台查看订单状态 |
| 信托受益人管理 | 新增/修改受益人会改变信托资料，通常需要审核或可追踪审批 |
| 信托文件管理 | 待上传、已批准、需要更新、已提交等状态依赖后台配置/审核 |
| 理财申购/赎回 | 是否需要 Admin 取决于产品规则；涉及资金和持仓变化，需要后台状态核对 |

## Admin Recon 新增阻塞项

| 阻塞项 | 实际证据 | 对本地执行的影响 | 对无人值守/CI 的影响 | 建议处理 |
| --- | --- | --- | --- | --- |
| Admin 图形验证码 | 登录页必须人工输入图形验证码；项目已使用独立 `npm run auth:admin` 采集 `auth/admin.json` | 登录态过期后需要人工重新采集一次 | CI 无法自行刷新登录态，不能依靠普通测试自动登录 | 提供测试环境专用的服务账号令牌、受控验证码 bypass 或 CI 预置/轮换 storageState；生产逻辑保持不变 |
| Admin storageState 会失效 | Admin fixture会检查缺失；TR-002预检进一步要求真实`法币资产管理 -> 资金互转`路由可用。2026-08-26重新采集后，业务路由预检与Dry Run均通过 | 当前状态有效；后续失效时会在Client提交前失败，不会卡在人工登录或产生TRF | 需要安全分发、有效期监控和定期人工/服务端刷新 | 失效时运行`npm run auth:admin`重新采集；所有Client+Admin写流程必须把目标业务路由纳入提交前health check，禁止只依据Cookie时间或缓存首页 |
| 缺少测试账号矩阵 | 当前只有单个具备资金和券商资格的共享账号；未确认企业、各地区开户、白名单、低风险/高风险理财专用账号 | 账号状态会随 Recon/E2E 被消耗 | 并发或重复运行会互相污染 | 建立每条流程独立账号池和状态清单，禁止多人共享同一待审核记录 |
| 缺少测试余额池 | 出金、互转、兑换、认购需要不同账户/币种的可用余额 | 小额写操作也会永久改变余额与账变 | 重跑会因余额变化产生非确定性 | 提供按用例预置余额、余额快照和重置接口 |
| 缺少可恢复业务数据 | 开户、券商开户、认购、赎回和转账会改变不可删除的状态 | 同一账号无法重复从初始状态开始 | 回归套件无法幂等 | 提供 DB fixture/reset API；反向交易不得视为回滚 |
| 入金无法跨端按业务编号搜索 | Client交易流水可读取系统`TXN-*`并打开详情，但Admin入账认领无Client TXN且只支持参考号、付款人、备注 | 不能通过编号直连，可能误认领同客户其他来账 | Client与Admin分别按业务指纹唯一定位；Admin仅在客户指纹+账户+币种+精确金额+状态+渠道+时间窗口候选恰好1条时允许处理 | 在Admin列表/详情回显Client TXN并支持精确搜索；现有代码保留`candidateCount===1`硬门禁 |
| 法币出金无法按业务编号搜索 | 出金审批搜索使用客户邮箱，未提供Client TXN精确搜索 | 需要邮箱+账户+币种+精确金额+状态+时间窗口，收款人在详情核对 | 候选不是1条时必须阻塞 | 增加TXN列和精确搜索；当前保留`candidateCount===1`及详情二次核对 |
| 资金互转候选唯一性 | Admin编号为`TXN-*`且搜索只支持客户/收款人，不能用Client `TRF-*`直接查询 | 只能用用户、账户方向、币种、精确金额、时间和待审核状态匹配 | 共享环境可能出现0条或多条候选；自动化必须停止 | 代码硬门禁`candidateCount === 1`并打开详情复核；产品后续可增加TRF/TXN关联字段或Client编号搜索 |
| 普通开户无法按申请编号搜索 | 开户审核只支持客户 ID/名称/邮箱 | 同一客户多账户申请时可能混淆 | 无法稳定处理并发申请 | 增加申请编号和账户类型筛选；详情回显 Client 编号 |
| 交易管理无法按交易编号搜索 | 列表显示交易编号，但筛选只有邮箱、日期、买入/卖出 | 需要转到账变流水核对 | 增加跨页面关联复杂度 | 增加交易编号精确搜索；短期以账变流水业务编号作为最终 Oracle |
| 法币出金批准凭证 | 审批要求打款渠道、银行、凭证、备注；项目已有固定Sandbox凭证并完成WD-003 | 本地受控批准可完成 | 仍不允许默认CI执行资金写操作 | 复用`test-assets/withdrawal/bank-payment-proof.png`与既有Approval Page Object |
| 法币出金手续费与实际扣款未形成数值 | 当前香港账户/USD在表单和确认态均显示`-`；历史记录虽有数值手续费，但不能代表当前配置 | WD-001可验证页面结构，WD-002/WD-003不能建立扣费与冻结金额Oracle | 资金用例不能安全判断余额是否足够或最终扣减是否正确 | 修复/配置`get-out-cash-fee`结果展示；在提交前返回数值fee、net和actual debit |
| 法币出金余额Oracle不可完整观察 | Client只显示availableBalance，未显示totalBalance或frozenBalance | 无法在只读阶段确认提交冻结的是requestedAmount还是requestedAmount+fee | WD-002首次真实执行前无法预设完整冻结/释放公式 | 提供可用/总额/冻结额字段或只读账变API；首次受控拒绝执行记录三阶段余额 |
| 法币出金待处理fixture | WD-002/WD-003执行期间已验证真实详情、拒绝和批准表单 | 历史终态不可重复执行 | 新Run必须自行创建唯一申请，创建后失败只允许Resume | 建立可重置待处理fixture仍有助于稳定Dry Run |
| 数字出金依赖 Safeheron | 页面明确标注 Safeheron；审核和链上完成状态分离 | 本地只能批准到托管处理中 | CI 无法保证链上完成时间和结果 | 使用 Safeheron Sandbox/测试网、可查询 TXHASH 的回调模拟器 |
| 地区账户与券商依赖第三方 | 美国Documenso/FATCA签署已成功，但Interlace/BaaS最终失败；新加坡 `sg_bank`；巴林渠道终态需在首次受控Run观察；券商预计 3–7 工作日 | L5不能作为秒级默认回归；美国进入BAAS_FAILED，Bahrain可在单次授权下进入Mutation Ready | CI无法保证所有第三方在单次流水内完成 | 使用受控轮询与Resume；提供provider stub/webhook simulator以支持CI |
| 拒绝原因约束不一致 | 普通开户选择拒绝后，备注为空仍可提交；理财认购拒绝原因是否必填未能安全验证 | 容易产生无原因拒绝 | 断言与真实规则不稳定 | 统一拒绝原因为后端必填，并在 UI 标星/禁用提交 |
| 状态枚举与筛选不一致 | 法币出金列表有`已拒绝`但筛选没有；开户说明不含已拒绝但列表存在 | 查询漏单 | 自动化状态覆盖不完整 | 统一 API 枚举、筛选项和页面说明 |
| 理财批准缺少二次确认 | Recon 实测`批准认购`点击即提交并返回成功，没有确认层 | 人工误触即可改变订单和余额 | 自动化 locator 误点会造成真实写入 | 增加包含订单号、客户、产品、金额的确认弹窗；写操作增加独立权限和审计 |
| 缺少自动清理/重置 | 管理端没有发现资金、订单、账户状态的测试重置入口 | Recon 后数据无法恢复 | 每次运行持续污染共享环境 | 提供仅测试环境可用、按业务编号授权的重置 API 和审计日志 |

## 业务编号精确定位能力

| 业务 | 精确能力 | 结论 |
| --- | --- | --- |
| 券商账户管理 | 支持客户/申请条件搜索；当前账号只有已开通记录 | 新申请仍需从Client读取真实编号并在Admin详情二次核对，且受第三方时长影响 |
| 理财认购/赎回 | 搜索框支持订单号 | 当前最好的 Client + Admin 订单关联能力 |
| 账变流水 | 支持业务交易编号/账变流水号 | 所有资金闭环的首选最终核对入口 |
| 法币账户审核 | 支持账户 ID | 可精确找到账户记录 |
| 数字地址白名单 | 支持地址 ID/地址 | 可精确找到地址记录 |
| 资金互转 | Client `TRF-*`与Admin `TXN-*`分离；按业务指纹匹配且候选必须唯一 | 可在唯一候选时受控审核，但无法保证共享环境每次产生唯一候选 |
| 入金认领 | 仅参考号/付款人/备注 | 缺少客户端业务编号关联 |
| 法币出金 | 仅客户/收款人/日期 | 缺少订单号关联 |
| 普通账户开户 | 仅客户 ID/名称/邮箱 | 同客户多申请存在歧义 |
| 交易管理/兑换 | 列表显示交易编号，搜索不支持 | 应转到账变流水按业务编号核对 |

## 推荐测试环境能力

1. 为每种业务提供可独占的测试账号、余额、账户状态和产品持仓 fixture。
2. 为银行、Safeheron、地区开户渠道、券商和签署系统提供 Sandbox 或 webhook simulator。
3. Client 提交接口必须回传稳定业务编号；所有 Admin 审核列表必须支持该编号精确搜索。
4. 提供按业务编号重置订单、账户状态、余额和第三方回调状态的受控 API，同时保留审计记录。
5. 所有 Admin 最终批准/拒绝按钮增加二次确认，确认层展示业务编号、客户、金额/产品和目标状态。

## 安全要求

- 不在测试报告、截图说明或文档中记录完整邮箱、密码、OTP、Cookie、Token、钱包 ID、银行卡号、券商账号、关联账户号、交易参考编号。
- 任何会提交订单、申请、资料变更或资金变动的用例必须使用显式标签和环境开关。
- 对资金类流程，默认只自动化到提交前确认页或费用预览；最终确认需要专用 Sandbox、数据清理和审批链路。
- 不通过增加 timeout、无条件 retry、忽略异常来掩盖接口 401、表单未渲染或登录态被破坏的问题。
