# Fidere Admin Business Flows

本文件记录 Admin Recon 实际看到的列表、详情、审核字段和状态。`已确认`表示页面或历史记录直接可见；`待验证`表示必须在专用 Sandbox 的受控 E2E 中建立因果关系，不能仅凭业务名称推断。

## 1. 入金与入账认领

| 项目 | Recon 结果 |
| --- | --- |
| 入口 | `运营` -> `法币资产管理` -> `入账认领` |
| URL | `/zh-CN/operation/fiatAssets`，tab 不改变 URL |
| 搜索方式 | 处理状态、匹配状态、日期；关键词支持参考号、付款人、备注 |
| 列表状态 | 筛选项：待处理、处理中、处理完成、处理失败；匹配状态：未匹配、已匹配 |
| 列表字段 | 提交时间、账户类型、币种/金额、实际入账金额、付款人、渠道、参考号、凭证、匹配客户、匹配状态、状态、操作 |
| 精确定位 | 无独立业务编号列，也不能按客户端`TXN-*`搜索；当前实现使用匹配客户不可逆哈希、账户、币种、精确金额、待处理状态、渠道和时间窗口，且强制`candidateCount===1` |
| 认领详情 | 原始来账金额、可认领入账金额、账户类型、付款人、渠道、参考号、提交时间、匹配客户 |
| 审核必填项 | `认领备注 *`；可认领金额为输入项 |
| 最终按钮 | `确认认领`；拒绝分支为 `确认拒绝` |
| 拒绝要求 | 页面明确提示拒绝必须填写原因，字段为`拒绝原因 *` |
| 二次确认 | 认领/拒绝抽屉本身即最终表单；未点击最终按钮，未确认后续是否还有确认层 |
| 后续状态 | 历史记录可见处理完成/处理失败；流水查询和对账中心存在对应记录 |
| 余额影响 | 业务上预期直接入账，历史流水支持该结论；本次未执行认领，仍需受控 E2E 验证认领时点和实际入账金额规则 |
| 第三方依赖 | 生产语义依赖银行来账、Wire/其他渠道和回调。Sandbox历史Client/Admin记录已能唯一Reconcile，但新Client提交是否无需外部回调仍待一次受控E2E确认 |
| 中间状态 | 待处理 -> 处理中 -> 处理完成/处理失败 |
| 建议断言 | 参考号和匹配客户正确；认领前余额；处理状态；认领后余额增量；法币流水；账变流水的业务编号、前后余额和手续费 |

**自动化风险**

- 缺少业务编号精确搜索，容易处理同客户的其他来账。
- `批量认领`会扩大影响范围，自动化禁止使用。
- 需要可注入的 Sandbox 来账、唯一参考号和清理/冲正能力。
- 当前历史只读Reconciliation已验证43条待处理记录中完整业务指纹最终唯一命中1条，并成功打开认领/拒绝抽屉；两个最终操作点击均为0。

## 2. 法币出金审批

| 项目 | Recon 结果 |
| --- | --- |
| 入口 | `运营` -> `法币资产管理` -> `出金审批` |
| 搜索方式 | 状态、日期、客户/收款人关键词 |
| 列表状态 | 筛选项含待处理、处理中、处理完成、处理失败、客户取消；历史列表还出现`已拒绝`，但筛选项未提供对应值 |
| 列表字段 | 申请时间、客户、账户类型、币种/金额、出金手续费、收款人、用途、状态、操作 |
| 精确定位 | 未显示业务编号，不能按业务编号精确搜索；只能按客户、收款人、时间、金额组合定位 |
| 详情字段 | 转账金额、实际到账金额、客户、账户类型、收款人、用途、申请时间、出金服务费、状态 |
| 审核必填项 | `打款渠道 *`、`打款银行 *`、打款凭证上传、`审批备注 *` |
| 最终按钮 | 审批抽屉底部`拒绝`、`批准` |
| 二次确认 | 未点击最终按钮；当前抽屉未显示独立的预确认步骤 |
| 后续状态 | 页面状态模型包含待处理、处理中、处理完成、处理失败、客户取消、已拒绝 |
| 余额影响 | 客户端提交后的冻结、拒绝释放、批准扣减未在只读 Admin Recon 中直接显示，必须在 Client 侧和账变流水中验证 |
| 第三方依赖 | 明确要求打款渠道、打款银行和凭证，说明批准并不等于外部银行已完成 |
| 中间状态 | 待处理/处理中与最终完成或失败并存，属于第三方中间状态流程 |
| 建议断言 | 客户端订单号、冻结金额、手续费、收款信息；Admin 状态；批准后的处理完成状态；拒绝原因；客户端冻结释放；账变与交易记录 |

**自动化风险**

- 无订单号搜索是当前最大误处理风险之一。
- 自动化不能伪造真实打款凭证；需要专用测试文件、测试银行渠道和可控回调。
- 状态筛选缺少`已拒绝`但列表存在该状态，需修复或明确 API 枚举。

## 4. 资金互转

| 项目 | Recon 结果 |
| --- | --- |
| 入口 | `运营` -> `法币资产管理` -> `资金互转` |
| 搜索方式 | 类型、状态、日期、客户/收款人关键词 |
| 类型 | 内部互转、用户间互转；历史记录还可见券商转信托、信托转券商、信托账户互转 |
| 状态 | 待审核、已批准、已拒绝 |
| 列表字段 | Admin `TXN-*`编号、记录类型、转出客户、收款人、转出账户、转入账户、币种、金额、手续费、实际到账金额、状态、提交/完成时间、操作 |
| 精确定位 | Client使用`TRF-*`，Admin使用`TXN-*`，未确认直接映射；搜索框也不支持Client编号。按用户、方向、币种、精确金额、时间窗口和待审核状态形成业务指纹，候选必须恰好1条 |
| 详情字段 | 当前状态、转出客户、Admin `TXN-*`编号、记录类型、转出/转入账户、币种、金额、手续费、实际到账金额、提交/完成时间 |
| 审核必填项 | `审核备注 *` |
| 最终按钮 | `拒绝`、`批准` |
| 二次确认 | 未点击最终按钮；当前审核抽屉未显示独立二次确认 |
| 后续状态 | 待审核 -> 已批准/已拒绝；批准记录带完成时间 |
| 余额影响 | 账变流水实际可见同一用户间转账的转出、转入、手续费及前后余额，确认会直接影响余额 |
| 第三方依赖 | 用户间内部互转可由平台内部完成；券商转信托/信托转券商是否等待券商侧结果，页面未给出明确回调状态，需产品和接口确认 |
| 建议断言 | 客户端申请编号；转出/转入账户；金额、手续费、实际到账；Admin 状态；成对账变；两端余额；客户端交易记录 |

**自动化风险**

- 具备业务编号但不支持按编号搜索，无法安全地只定位本次自动化订单。
- 当前账号有券商互转资格，后续需固定该账号或建立可重复的券商已开户数据。
- 反向转账只能形成新账变，不能删除原记录，不能视为真正的数据恢复。

## 5. 美国、新加坡、巴林等法币账户开户

| 项目 | Recon 结果 |
| --- | --- |
| 入口 | `KYC审核` -> `开户审核` |
| 搜索方式 | 客户 ID、客户名称、客户邮箱；状态筛选；个人/企业 tab |
| 列表状态 | 待提交、审核中、审核通过、已拒绝。页面说明与实际列表存在差异：说明称只含前三种，实际可见已拒绝 |
| 列表字段 | 客户信息、提交日期、状态、操作 |
| 精确定位 | 不支持申请编号；同一客户多账户申请时需结合客户、账户类型、时间和详情识别 |
| 详情字段 | 客户身份、地址、证件、自拍、地址证明、资金来源；美国账户还显示 FATCA 第三方文档签署状态 |
| 审核步骤 | `开始处理` -> 检查/必要时修改右侧用户资料 -> 选择审核决定 -> 填写审核备注 -> 提交 |
| 审核必填项 | `审核决定`必选；审核备注未标星。Recon 选择“拒绝申请”后，即使备注为空提交按钮仍可用，拒绝原因未被 UI 强制 |
| 最终按钮 | `保存修改并提交审核` |
| 二次确认 | 未点击最终按钮；处理页未展示独立确认层 |
| 后续状态 | 待提交/审核中 -> 审核通过或已拒绝；外部开户是否另有处理中状态未在此列表明确展示 |
| 余额影响 | 账户配置包含开户费，客户端历史也存在开户费类型；费用扣除的触发时点未在本次 Recon 建立因果关系 |
| 第三方依赖 | 美国账户渠道为 `interlace` 且需要资料/FATCA；新加坡为 `sg_bank`；巴林为 `EU_BLANK`，该名称需确认是否为占位配置 |
| 建议断言 | 申请客户与账户类型；文件完整性；Admin 决定/备注；客户端账户状态；外部开户状态；开户费账变；拒绝原因展示 |

## 7. 理财认购

| 项目 | Recon 结果 |
| --- | --- |
| 入口 | `业务配置` -> `理财产品` -> `认购管理` |
| 搜索方式 | 客户、订单号、产品；待审核/已通过/已拒绝 tab |
| 列表字段 | 客户/订单、产品/风险、首次或追加认购、付款账户、金额、申请时间、审批状态、操作 |
| 精确定位 | 支持订单号搜索，可安全关联客户端创建的本次订单 |
| 详情字段 | 订单状态、认购金额、手续费、订单号、客户、付款账户、认购类型、风险级别、申请/审批时间、处理记录 |
| 最终按钮 | `拒绝`、`批准认购` |
| 拒绝要求 | 拒绝弹层显示`拒绝原因`和 500 字限制；未提交，是否强制必填仍待验证 |
| 二次确认 | **已确认没有二次确认**：`批准认购`会立即执行并显示成功提示 |
| 后续状态 | 待审核 -> 已通过/已拒绝 |
| 余额影响 | 账变流水实际可见`理财认购`扣减、交易前后余额；持仓生成时点需 Client 侧验证 |
| 第三方依赖 | 产品和托管结算规则未在 Admin 页面显示，需按具体产品确认 |
| 建议断言 | 订单号、产品、金额、手续费、付款账户；Admin 状态；认购账变；客户端持仓和交易记录 |

> Recon 事件：为检查是否存在二次确认，本次误触第一条待审核记录的`批准认购`，页面直接返回成功。未尝试回滚。该事件证明按钮缺少安全确认层，后续只读工具不得点击它。

## 9. 兑换

| 项目 | Recon 结果 |
| --- | --- |
| Admin 入口 | `运营` -> `交易管理`；余额明细在`账变流水` |
| 交易搜索 | 用户邮箱、日期、交易类型（全部/买入/卖出）；列表显示交易编号但不支持按编号搜索 |
| 交易字段 | 编号、用户、交易编号、交易类型、来源资产、目标资产、交易时间、交易状态 |
| Admin 审核 | 未发现兑换审核、批准或人工处理入口；历史兑换均作为成功交易展示 |
| 状态与余额 | 账变流水可见同一 OTC 兑换的卖出资产减少和买入资产增加，并展示业务交易编号、前后余额和手续费 |
| 第三方依赖 | 报价/汇率服务存在，但管理端未显示人工中间状态 |
| 结论 | 兑换是客户端即时流程，Admin 仅只读记录和账变核对 |
| 建议断言 | 客户端报价、到账金额和成功状态；交易列表来源/目标资产；账变按业务编号精确命中两条或对应关联记录；前后余额守恒 |

## 10. 交易记录与账变流水

| 页面 | 关键能力 | 自动化用途 |
| --- | --- | --- |
| 交易管理 | 业务级交易列表；支持邮箱、日期、买入/卖出；不支持交易编号搜索 | 客户端交易结果的运营侧只读验证；不适合仅凭编号定位 |
| 法币流水查询 | 支持日期、客户 ID、类型、状态、关键词；含渠道、参考号和状态 | 入金、出金、互转的运营流水验证 |
| 数字资产流水 | 支持客户、币种、网络、方向、状态、金额、来源、关键词；含 TXHASH | 数字入金/出金和链上完成状态验证 |
| 账变流水 | 支持`业务交易编号 / 账变流水号`精确查询；详情含业务编号、前后余额、手续费和关联账变 | 所有余额变化的最终财务断言，应作为资金 E2E 的核心 Oracle |

## 11. 法币账户、白名单与客户资料

| 业务 | Admin 入口 | 精确搜索 | 最终操作 | 依赖/备注 |
| --- | --- | --- | --- | --- |
| 客户 KYC | 案件工作台、处理中审核、用户管理 | 客户名称/ID/编号，入口间能力不同 | KYC 处理页 | Sumsub；客户详情含三方状态和操作记录 |
| 收款法币账户审核 | 法币账户审核 | 账户 ID、用户名、账号 | 详情页`拒绝`/`通过` | 按账户 ID 可精确查找；按钮可能直接提交，未点击 |
| 数字地址白名单 | 数字资产地址审核 | 地址 ID、用户名、地址 | 详情审核 | 地址/网络可精确关联；属于数字出金前置数据 |
| 信托资料 | 信托管理 | 信托名称、编号、用户名 | 详情内处理 | 受益人和文件状态需要专用可恢复数据 |

## 12. 手续费与账户配置

- `账户类型配置`维护地区、渠道、主/支持币种、开户费和资料要求；修改会影响客户端开户与扣费，Recon 未修改。
- `提现服务费配置`支持用户级计费方式和平台默认规则；修改会影响出金实际到账，Recon 未修改。
- `费率中心`支持用户级法币/数币兑换费率；修改会影响报价，Recon 未修改。
- `券商配置`维护开户费、资料数和预计处理时间；修改会影响开户流程，Recon 未修改。
- `理财产品`的产品列表可上/下架并维护产品；Recon 只查看，未新增或编辑。

## 自动化可行性分类

| 分类 | 业务 | 理由 |
| --- | --- | --- |
| A. Client 完全自动化 | 兑换成功闭环；客户端只读页面/报价前校验 | 兑换无 Admin 审核，Admin 只用于交易和账变核对；仍需专用余额与报价稳定性 |
| B. Client + Admin 联动 | 资金互转、理财认购/赎回、法币账户审核、数字地址白名单、开户审核 | Admin 有明确待审核列表和最终处理动作 |
| B. Client + Admin 联动 | 法币入账认领 | 有明确认领和拒绝链路，但需要先产生可控来账 |
| C. 只能部分自动化 | 法币出金、数字资产出金、美国/新加坡/巴林开户、券商开户 | 依赖银行、Safeheron、Interlace/地区渠道、券商或签署系统及回调 |
| D. 当前无法稳定自动化 | 无业务编号搜索的法币入金/出金和资金互转批准路径；任何需要数据回滚的资金写操作 | 缺少安全精确定位、Sandbox、测试数据重置和自动清理能力 |

## 共同安全门槛

1. Client提交后保存Client业务编号；若Admin使用不同编号或不支持搜索，不得仅按列表第一行/最新一行处理，也不得替换编号前缀推导。
2. Admin处理前再次断言客户、精确金额、币种、账户方向、创建时间和待审核状态；业务指纹候选必须恰好1条。
3. 资金写操作必须运行在专用 Sandbox 账号，并有显式环境开关和单线程执行。
4. 处理后以客户端状态、交易记录和账变流水三方一致为完成条件。
5. 没有重置 API 时，不得把“反向交易”或“再申请一次”当作数据清理。
